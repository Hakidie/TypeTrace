# Backend Architecture & Conventions

> Instruction doc for AI agents and developers. Read this before adding or changing backend code. Follow these patterns exactly — do not introduce new architectural styles without reason. The reference feature is `notes` (`*/note.*`). This is a base project for students: keep code simple, reuse the helpers below, and update this file when a convention changes.

## Stack

- **Runtime**: Node.js + Express 5
- **Language**: TypeScript (strict mode, CommonJS output)
- **Database**: MongoDB via Mongoose 9
- **Auth**: JWT (Bearer token); optional email OTP at login, per user (`loginOtpEnabled`)
- **Validation**: Zod 4 (requests and environment)
- **Media**: Cloudinary (images via Multer memory storage), optional
- **Email**: Nodemailer (SMTP), printed to the console when SMTP is not configured
- **Security**: helmet, CORS locked to `CLIENT_URL`, rate limits · **Logging**: morgan
- **Dev**: `tsx watch` · **Build**: `tsc` → `build/` · **Start**: `node build/server.js` · **Test**: Vitest + supertest + mongodb-memory-server

## Layered (Clean) Architecture

Request flows strictly top-to-bottom. Never skip a layer or call upward.

```
HTTP request
  → routes/         endpoints + middleware chain
  → middlewares/    authGuard → requireRole → validate → (imageUpload)
  → controllers/    read req, call service, shape res
  → services/       queries, ownership rules, side effects (email, cloudinary)
  → models/         Mongoose schemas
  → config/         env, db, cloudinary clients
  → utils/          app-error, pagination, jwt, hash, otp, vietnamese-errors, english-errors, passage-text, local-date
```

| Layer | Owns | Must NOT |
|-------|------|----------|
| `routes/` | URL + verb + middleware chain | contain logic |
| `controllers/` | req/res handling, status codes | contain queries beyond one trivial call; be reused |
| `services/` | queries, access rules, workflows, side effects | touch `req`/`res` |
| `models/` | schema, constraints, `toJSON` hiding private fields | contain HTTP concerns |
| `validators/` | Zod schemas + inferred input types | run queries |
| `middlewares/` | auth, roles, validation, upload, errors | contain feature logic |
| `utils/` | pure helpers | import services |
| `config/` | env parsing, clients | contain feature logic |

## Naming Conventions

- Files: `kebab-case` with layer suffix — `note.controller.ts`, `lesson-plan.validator.ts`.
- Routers: `<feature>Router`. Models: `<Name>Model` + `<Name>Document`.
- Controllers: named exports, one per endpoint (`listNotes`, `createNote`).
- Validators: `<action>Schema` + inferred `<Action>Input` type.

## Core Patterns

### 1. Environment (`config/env.ts`)
All variables are parsed by one Zod schema; startup fails with a list of every invalid variable. In production `JWT_SECRET` must be ≥ 32 characters and not the example value. Add new variables to the schema and to `.env.example`. Never read `process.env` elsewhere.

### 2. Routes → middleware chain

```ts
noteRouter.use(authGuard, requireRole('user', 'admin'));          // all routes: signed in, role loaded
noteRouter.get('/', validate({ query: listNotesQuerySchema }), listNotes);
noteRouter.patch('/:id', validate({ params: idParamsSchema, body: updateNoteSchema }), updateNote);
profileRouter.post('/avatar', authGuard, imageUpload.single('avatar'), uploadAvatar);
```
Mount in `app.ts`: `app.use('/api/<plural>', <name>Router)` (before `notFoundHandler`). `npm run gen:module` does this for you.

### 3. Validation (`validate`)
`validate({ body?, query?, params? })` parses each part with Zod and replaces it with the parsed value, so `req.query.page` is a number. Failures answer `400 { message: 'Validation failed', errors: [{ field, message }] }`. `validateBody(schema)` is shorthand for `validate({ body: schema })`.

### 4. Auth and roles
- `authGuard` verifies `Authorization: Bearer <token>`, sets `req.user = { sub, email }` and reads the user's `status` from the database: a locked account answers 403 `Your account is locked`, also with a token issued before the lock (a token of a deleted user passes; the handlers answer 404). Login and Google login answer 403 for a locked account too (after the password check, so a wrong password stays 401).
- `requireRole(...roles)` loads the user's role from the database (so promotions apply without re-login), sets `req.user.role`, and answers 403 otherwise.
- Login: password check → if `user.loginOtpEnabled`, email an OTP (202 `{ requiresOtp }`), else return `{ token }`. Users toggle it with `PATCH /api/profile/security`.
- Profile picture: `POST /api/profile/avatar` uploads an image (Cloudinary) and shows it; `PATCH /api/profile/avatar-source` with `{ avatarSource: 'picture' | 'pixel' }` chooses what the account shows, its uploaded picture or its pixel avatar (`avatarSource` on the user, default `picture`). The picture is kept while the pixel avatar is shown; `picture` answers 400 when none was uploaded.
- `GET /api/auth/email-exists?email=` (public, auth rate limit) answers `{ exists: boolean }` for the register form. `register` already tells a taken email with 409, so this adds no new information, only earlier.
- Google login (`POST /api/auth/google` `{ credential }`) answers `{ token, isNewUser }`: `isNewUser` is true when this login created the account (`findOrCreateGoogleUser`), and the app then starts Ping's tour for the new learner, like after a registration (`POST /api/tutorial/start`).

### 5. Controllers — thin

```ts
const actorOf = (req: Request) => ({ id: req.user!.sub, role: req.user!.role });
export const updateNote = async (req: Request, res: Response) => {
  res.json(await noteService.updateNote(actorOf(req), req.params.id as string, req.body as UpdateNoteInput));
};
```
No try/catch: Express 5 forwards rejected promises to the error handler.

### 6. Services — queries and access rules

```ts
const accessFilter = (actor: Actor, id?: string) => ({ ...(id ? { _id: id } : {}), ...(isAdmin(actor) ? {} : { owner: actor.id }) });
export const updateNote = async (actor: Actor, id: string, input: UpdateNoteInput) => {
  const note = await NoteModel.findOneAndUpdate(accessFilter(actor, id), input, { new: true, runValidators: true });
  if (!note) throw notFound('Note not found');   // also for other users' notes: never reveal they exist
  return note;
};
```

### 7. Lists (`utils/pagination.ts`)
Extend `paginationQuerySchema` (`page`, `limit ≤ 100`, `sort` like `-createdAt`) and declare the sortable fields with `sort: sortSchema(['createdAt', 'title'])` (anything else answers 400 — never list private fields). Return `paginate(Model, filter, query)` → `{ items, page, limit, total, totalPages }`. Ties are broken by `_id`, so pages never overlap. Escape user text before building a `RegExp` (see `note.service.ts`). An optional fourth argument: `{ select: 'title wordCount' }` sends only those fields (use it when `toJSON` keeps a field this user may not see, like the `owner` of a passage) and `{ collation: { locale: 'vi' } }` sorts text in Vietnamese order (Đ right after D, not after Z); see `listPassages` in `passage.service.ts`. A query with a collation can only use the indexes that have the same collation: give it one (see the `{ locale: 'vi' }` index in `passage.model.ts`), or MongoDB reads the whole collection. `paginate` counts with the same collation, so that index serves the count as well as the page.

### 7b. Admin endpoints (`routes/admin.route.ts`)
All under `/api/admin`. **Guarded by `adminRouter.use(authGuard, requireRole('admin'))`: admins only, other accounts get 403.** Endpoints: `GET /stats`, `GET /users` (search `q`, filters `role`, `verified`, `status`, allowlisted `sort`, pagination), each user with `stats` (`{ wpm, accuracy }`, the average of their completed typing sessions; absent when there is none) and `sessions` (`[{ date, sessions }]`: completed typing sessions, counted or not, per UTC day of `completedAt` for the last 371 days, read from `TypingSession`; both from `typingActivityOf` in `typing-session.service.ts`; the profile's `GET /api/sessions/activity` shares only the averages and reads its days from DailyProgress in the learner's zone, see 7c and 7g, so the two can differ), `GET|PATCH|DELETE /users/:id` (`PATCH` takes `displayName`, `bio` (200 characters at most, empty clears it), `role`, `isEmailVerified`, `loginOtpEnabled`), `PATCH /users/:id/status` (`{ status: 'active' | 'locked' }`; sets or clears `lockedAt`; locking yourself answers 400, locking an admin 403), `POST /users/bulk-delete` (`{ ids }`, `bulkIdsSchema`). Deleting a user also deletes their notes, typing sessions and their replays (7c), days (DailyProgress), daily tasks (UserDailyTasks, 7i) and avatar. The signed-in account can never remove its own admin role or delete itself (checked in `admin-user.service.ts`, keep it). Yes/no filters use `optionalBooleanQuerySchema` (missing = no filter).

**Passage bank** (`admin-passage.{validator,service,controller}.ts`, same router): `GET /passages` (search `q` in title and source through `titleSearchPattern`, accents optional like the learner list, so `ha noi` finds `Hà Nội`; filters `status`, `visibility`, `isPlacement` and `isRanked`, allowlisted `sort`, titles in Vietnamese order with the `{ locale: 'vi' }` collation (only for `sort=title|-title`: a query with a collation can only use the indexes with the same one), pagination; the admin page asks for `visibility=public`, so its bank holds TypeTrace's and the approved passages, never a learner's private one), `POST /passages` (`{ title, content, source, isPlacement? }` → 201, always a `draft` owned by TypeTrace; a `status` in the body is ignored), `GET|PATCH|DELETE /passages/:id`, `PATCH /passages/:id/status` (`{ status }`). `draft`, `published` and `archived` switch freely in any direction (the same status, `pending` and `rejected` answer 409; learners' requests are decided with approve / reject). A ranked passage (`isRanked`, US6.4, English only (400 otherwise, also when a ranked passage is turned Vietnamese); the ranked duels play only these, race (`pickRankedPassage`) and word rain (`pickRainWords`) alike, not the placement test; `npm run migrate:ranked-passages` marks the English passages already in the bank, and `passages-en.ts` seeds them marked; set with `PATCH /passages/:id`; a learner gets 403 like on every admin route) must be `published`: marking a draft or archived passage, or creating one with `isRanked: true`, answers 409, and so does moving a ranked passage out of `published` (remove the mark first). Once a duel has started on it (a `Match` with this `passageId` and a `startedAt`), its `content` and `language` can no longer change (409); title and source still can. A placement passage (`isPlacement`, Vietnamese only) may be archived like any other, but it cannot be deleted (a placement test needs passages: archiving all of them makes `GET /api/placement` answer 404). `DELETE` is a hard delete (the admin page offers it on archived passages that are not placement passages only, on the card and in the edit form, SCRUM-159) and answers 409 for a passage learners have typed (a session where the first key was pressed, `beganAt`, or a completed one: their history): archive it instead. The sessions only opened on it and never typed in (the Typing page starts one as soon as it shows a passage, abandoned when the learner opens another) do not count and are deleted with it. Edits use `doc.save()` so `wordCount` and `tagCounts` are counted again. Learners only ever get `published` passages (`typing-session.service.ts`), apart from their own passages waiting for review or turned down. `npm run import:passages` adds starter passages as `published` and moves old `active`/`inactive` passages to `published`/`archived`.

**Review of learners' passages** (SCRUM-176, same files and router): a learner asks for one of their private passages to become public (7e), which puts it in `pending`. The status endpoint never moves a passage into or out of `pending` or `rejected` (409): an admin answers with `PATCH /passages/:id/approve` (→ `published` and `public`, `reviewNote` cleared, so every learner can type it; `ownerName` becomes `publicOwnerName` of its owner as they are now: their display name, `ANONYMOUS_OWNER_NAME` = `Anonymous learner` without one, `TypeTrace` for an admin, never the email that `ownerFieldsFor` puts on a private passage of a learner without a display name, which only they and admins see) or `PATCH /passages/:id/reject` `{ reason }` (→ `rejected` and still `private`, the trimmed `reason` saved in `reviewNote`, 1 to `REVIEW_NOTE_MAX` = 300 characters; never `published`, so `?status=published` does not list it; the learner sees the reason, may still type and edit it, and may ask again). Both are one conditional update on `status: 'pending'`, so two admins (or an admin and the learner taking the request back) cannot both win: not pending → 409, unknown id → 404. `POST /passages/bulk-approve` `{ ids }` and `POST /passages/bulk-reject` `{ ids, reason }` change only the passages of `ids` still pending and answer `{ updated }` (bulk approve writes one conditional update per passage, each with its own author's public name). The review queue is `GET /passages?status=pending` (`q`, pages, `sort=updatedAt` = oldest request first: a request updates the passage; index `{ status, updatedAt }`), whose items carry the text and `ownerName`. **Edits of public passages** (a learner edited an approved passage, 7e) are in the same queue: `?status=pending` also lists the passages with a `pendingEdit` (`status` is still `published`, `visibility` `public`; the item carries `pendingEdit` next to the approved text). `approve` replaces `title`, `source` and `content` with the edit, counts `wordCount` and `tagCounts` again, and clears `pendingEdit` and `reviewNote`; `reject` drops the edit, keeps the approved text and saves the reason in `reviewNote` (the passage stays public). `?status=pending&edited=true` keeps only the edits and `edited=false` only the requests to make a passage public. Single and bulk decisions work on both kinds; each is one conditional update (an edit only if it is still the same edit that was read, so an edit sent again meanwhile is not approved unread), and the 409 / 404 rules are the same.

**Daily tasks** (SCRUM-210, `admin-daily-task.{validator,service,controller}.ts`, same router): `GET|POST /daily-tasks`, `GET|PATCH|DELETE /daily-tasks/:id` and `GET|PUT /daily-tasks/settings`; see 7h.

### 7c. Typing sessions (`/api/sessions`)
A learner types a passage from the `Passage` collection (`passage.model.ts`, filled by `npm run import:passages`). Files: `typing-session.{model,validator,service,controller,route}.ts`; word grading uses the set of the session's `language` (`utils/typing-language.ts`: `vietnamese-errors.ts` or `english-errors.ts`, 7m). Always owner-only: another user's session answers 404, even for admins. Completing a session is one conditional update on `status: 'in_progress'`, and a counted one is then added to the learner's day, once (DailyProgress, 7g), and to their daily tasks (7i). Abandoning one is a conditional update too, so a session completed in the meantime stays completed.
- `POST /` `{ mode?, passageId?, timeLimitSeconds?, errorType? }` → 201; any other field (a `status`, a `visibility`) is ignored. `mode` is `practice` (default), `placement` or `targeted` (Weak spots: a lesson of the word bank instead of a passage, with an optional `errorType` and never a `passageId`, see 7c-targeted). Picks the passage: the one in `passageId` (must be in the list of its `mode` from `GET /api/passages`, see 7e, which also holds the learner's own passages waiting for review; else 400), a random published placement passage (`isPlacement`) in `placement` mode, otherwise a random published public practice passage of the learner's typing language (`practiceLanguageFilter`, 7e; 404 if there is none of the kind asked for). The session keeps its `language` (SCRUM-219): in practice the learner's `settings.typingLanguage` at that moment (`typingLanguageOf`), in placement and in Weak spots always `vi` (the word bank and its lessons are Vietnamese, so a learner who types English still gets a Vietnamese lesson, and its random passage when there is nothing to aim at is a Vietnamese one); a session saved before the field has none and is Vietnamese, so the readers filter with `sessionsIn(language)` (`{ language: { $ne: 'en' } }` for `vi`), and no migration is needed. Copies the passage words (`targetWords`) and title (`passageTitle`) into the session and turns the learner's older `in_progress` session into `abandoned`. `timeLimitSeconds` (one of `TIME_LIMIT_CHOICES_SECONDS`: 10, 20, 30, 60, 120, 180, else 400) is the time the learner chose, kept as `chosenLimitSeconds` (US10.1); it cannot change afterwards: the Placement page starts a new session (with a passage chosen again) when the time changes. An `abandoned` session is deleted 24 hours after it was abandoned (`ABANDONED_TTL_MS`, a partial TTL index on `updatedAt` for `status: 'abandoned'`; completed sessions are never deleted).
- `PATCH /:id/begin` → the learner pressed the first key: stores `beganAt` once (a second call keeps the first time; not in progress → 409). The timer starts here, not when the session was created. Any body is ignored: the chosen time is fixed when the session starts.
- `PATCH /:id/complete` `{ typedWords }` → the server grades again with the set of the session's `language` (`classifyIn`; `errorCounts` and `opportunityCounts` hold the types of that set only, SCRUM-219), computes `wpm` (the international standard, SCRUM-232: the characters of the correct words plus the space between them, counted as shown (NFC) by `countWpmChars`, divided by 5 (`CHARS_PER_WORD`) per minute in `computeWpm`; duration measured by the server from `beganAt`, or from `startedAt` if `begin` was never called), `accuracy`, `errorCounts`, `opportunityCounts` and `isCounted` (at least 20 words, at most 200 WPM, and not longer than 3 minutes). A session lasts at most 3 minutes (`MAX_SESSION_MS`): a request that arrives within 5 seconds of the limit gets `durationMs` capped at 3:00; a later one is saved with its real duration but not counted. It ignores any total the client sends. Not in progress → 409; more words than the passage → 400. Optional `typedAtMs` (SCRUM-187): one time per typed word, in ms after the first key, saved as `SessionWord.typedAtMs` (older sessions have none); the times must not go back, be negative or later than `durationMs` plus the 5 s grace (the clock starts at `begin`, which arrives a little after the first key), else 400, and the count must equal the number of words.
- Placement leaderboard flag (US10.1): `complete` also sets `isOnPlacementBoard` by `isSessionOnPlacementBoard`: a counted `placement` session, with `chosenLimitSeconds` of 3 minutes (`PLACEMENT_BOARD_LIMIT_SECONDS`), accuracy of `minAccuracy` or more (the app setting `placementMinAccuracy`, default 90, whole number 50 to 100, read by `getAppSettings` only for placement sessions), that either lasted the 3 minutes (`durationMs` is the server's own clock) or typed every word of the passage. The `timeLimitSeconds` that `complete` receives is only for the chart and is never read for this. When an admin saves a new minimum, `rebuildPlacementBoardFlags` sets the flag again on every completed placement session (see 7d); `completeSession` also reads the minimum again after saving its own flag and fixes it if it changed meanwhile. Sessions from before the flag have none until `npm run migrate:placement-board` is run.
- Replay (SCRUM-35): `complete` also takes an optional `replay`, the changes of the text the learner saw while typing (`ReplayEvent` in `session-replay.model.ts`: `[ms since the previous change, position, characters removed, text inserted]`, plus `1` while the input method still composes it, so the graded words stay as they were), at most `MAX_REPLAY_BYTES` (64 KB) of JSON. The request that completes the session saves it apart, in `SessionReplay` (`{ owner, session, events }`, one per session, `session-replay.service.ts`); the session never points to it, so the history and the stats never read it. A replay is extra: one that breaks a rule is dropped (`.catch(undefined)` in `completeSessionSchema`) and a failed save is logged, and neither stops the completion. A TTL index on `createdAt` lets MongoDB delete it 30 days later (`REPLAY_TTL_DAYS`). `GET /:id/replay` → `{ session, events, createdAt, expiresAt }`; owner only (another user, even an admin, 404), and 404 for a session without a replay and for a replay older than 30 days, also in the minute before the TTL monitor deletes it.
- `PATCH /:id/abandon` (409 if not in progress), `GET /:id`, `GET /` (history for the profile page, `status`, `mode` and `timeLimitSeconds` (seconds, 1-180) filters, `q` = text searched in `passageTitle` through `titleSearchPattern` (accents optional), `sort` by `createdAt|wpm|accuracy`, pagination; each item is a summary: `mode`, `language` (SCRUM-219; missing on a session from before: Vietnamese), `passageTitle`, `status`, `wpm`, `accuracy`, `durationMs`, `timeLimitSeconds`, `isCounted`, the dates and the speed `timeline` (as in the stats, worked out from the words, which are read for it but never sent), never the `words` and `targetWords` that `GET /:id` has).
- `GET /:id/stats` → the numbers behind the result charts (SCRUM-186): `{ totalWords, correctWords, wrongWords, wrongRate, errorTypes: [{ type, errors, opportunities, rate }], isCounted }`, worked out again by `getSessionStats` from the graded `words` (`countErrors`), never from the stored totals; the types are the ones of the session's language (SCRUM-219), and the ones without any opportunity are left out. plus `timeline: { status, points }` (SCRUM-187): `points` = `[{ second, wpm, errors }]` every second and at the end, over a sliding window of the last `TIMELINE_WINDOW_SECONDS` (10) seconds, from `typedAtMs` by `timelineOf` (WPM = characters / 5 per minute of the window like `computeWpm`, cut at the start; `errors` = the wrong words finished since the previous point, not windowed: each mistake is on one second only, drawn as a cross), so it shows the pace at that moment and the last point is no longer the session WPM; `status` is `no_data` (an older session without times), `too_short` (under 10 s) or `ok`. `timeLimitSeconds` = the time the learner chose (the page sends it with `complete`, 1-180, only to size the chart's time axis; 180 for a session without it). Both lines are computed by the server, nothing from the client. Owner only (another user, even an admin, 404); a session that is not `completed` answers 409.
- `GET /activity?language=vi|en` → the learner's own `{ stats?, language, timezone, sessions }` for their profile page (SCRUM-157, SCRUM-31): `stats` = `{ wpm, accuracy }`, the averages of all their completed sessions of `language` (SCRUM-219: the one asked for, their `settings.typingLanguage` when missing, sent back as `language`; absent before the first one; in Vietnamese the same numbers as their row in the admin user list, which averages Vietnamese sessions only), `timezone` = their `settings.timezone` (the dates are days in this zone), `sessions` = `[{ date, sessions, tasksTotal?, tasksDone? }]`, their DailyProgress rows (counted sessions only, 7g), each with how many daily tasks (7i) the day had and how many were completed on its numbers (`taskCountsSince`, left out on a day without tasks) of the last `HEATMAP_DAYS` (371) days, today included, oldest first; a new learner gets `{ language, timezone, sessions: [] }`. The days count the sessions of both languages. The admin list still counts every completed session per UTC day from `TypingSession` (7b), so its numbers can differ. Declared before `GET /:id`, which would take `activity` for an id.

### 7c-targeted. Weak spots (`POST /api/sessions` in `targeted` mode, SCRUM-28, US3.2)
A practice lesson aimed at the learner's errors instead of a passage: words picked from the word bank (`Word`, `npm run import:words`), then a passage that makes sense, which the AI writes from them. File: `services/targeted-practice.service.ts`, which imports models, `ai.service`, `error-profile.service` and `passage-lock.service` but never the typing sessions, so no service cycle starts (`startSession` calls its `lessonFor`); the AI writer's prompt and limits are in `config/weak-spots-ai.ts`. The page shows cards first (the auto lesson and the five error types, SCRUM-74), each starting a lesson.
- Request: `{ mode: 'targeted', errorType?, timeLimitSeconds? }`; a `passageId` in this mode, or an `errorType` in another one, answers 400 (`createSessionSchema`). The learner's plan needs `canCreateErrorPractice` (`AppSettings.plans`, 7n; Premium by default), else 403 `Your plan does not include weak spots practice`, checked first (`assertCanPracticeWeakSpots`).
- Focus: `errorType` (any of the five, weak or not), else `getTopErrorTypes(userId, LESSON_FOCUS_TYPES)`: the 2 types of the Vietnamese error profile (7i-b; its Vietnamese sessions only, whatever the learner types in Practice, SCRUM-219) with the highest error rates among the types with enough data, weak or not, highest first (an error profile is enough: no type has to reach the weak line). The session is always `language: 'vi'`.
- Lesson (`buildLesson`, pure; it takes a `random` so the tests can fix it): a random size from `LESSON_MIN_WORDS` to `LESSON_MAX_WORDS` (30 to 50), of which ⌈60 n / 100⌉ to ⌊70 n / 100⌋ (`LESSON_MIN_FOCUS_PERCENT`, `LESSON_MAX_FOCUS_PERCENT`, whole numbers) train the focus, the types taking turns (a type without a word left gives its turn to the next), and the rest train none of it; then the words are shuffled. Which words train a type (`trainsErrorType`): the word's `tags` for `D_MISSING`, `MARK_WRONG` and `HOI_NGA_CONFUSION`; `TONE_WRONG` and `BASE_LETTER` are on every word (`tagWord` counts chances), so a tone is trained by a word with a tone mark and the letters by any word (a lesson for the letters is made of any words, all of them training it). Only active words (`isActive: true`; an admin hides a word with `false`); the bank is read whole (text and tags), it has hundreds of words.
- Recent words: the picked words (`lessonWords`; the `targetWords` of a lesson saved before the AI passages, which were the picked words) of the learner's last `RECENT_LESSONS` (3) lessons, in progress, abandoned or completed (`mode: 'targeted'` with a non-empty `focusErrorTypes`, newest `createdAt` first, index `{ owner, mode, createdAt }`), are taken only once no group has another word left; once every word of the groups is in the lesson, words repeat (a bank too small for the lesson). The words of an AI passage are never left out: only the picked ones.
- AI passage: Gemini (`generateText` in `ai.service.ts`, the chat's key and model) gets the practice words (the picked words that train the focus, "Từ cần luyện") and the others ("Từ gợi ý") with `weakSpotsAi.systemPrompt`, `maxOutputTokens` 1024 and an 8 s timeout. `checkAiPassage` (pure) takes the answer through `cleanAiText` (no Markdown, no quotation marks around it, `cleanPassageText`) and accepts it with `minWords` to `maxWords` words (20 to 200; 20 so the session can still count) that use at least `minUsedPercent` (60) % of the practice words (case and punctuation ignored, compared in whole numbers). Natural text cannot reach 60 % of its own words for đ (11 % in the starter passages) or hỏi / ngã (18 %), so the check counts the practice words used, not the share of the passage. Otherwise the lesson is the picked words, with no error for the learner: no key (no request), over `weakSpotsAi.perMinute` (5) AI lessons a minute for this learner (`lessonAiLimiter` in `typing-session.route.ts`, an `express-rate-limit` whose handler lets the request go on with `res.locals.aiLimited` instead of a 429), a 429, 4xx or 5xx from Gemini, a timeout, an empty or refused answer. Each failure is logged as a warning. The passage stays in the session: it is never saved as a `Passage`.
- Session: `mode: 'targeted'`, no `passageId` (it is required in every other mode), `passageTitle` = `lessonTitle(focus)` ("Weak spots: hỏi / ngã, đ"), `targetWords` = what is typed (the AI passage, or the picked words), `lessonWords` = the picked words, `lessonSource` = `ai`, `words` or `passage` (never shown: the learner sees no AI failure), `focusErrorTypes` = the types of the focus that have words. Nothing to aim at (no `errorType` and no type with enough data in the error profile yet, or no active word for the focus): a random published public Vietnamese practice passage, as Random in Practice gives (`pickPassage` with `vi`, plans and locks apply), with `focusErrorTypes: []`, and the page tells the learner why. The field has no default, so only Weak spots sessions have it and `[]` always means "nothing to aim at".
- From then on a lesson is a session like Practice: `begin`, `complete` (graded, counted from 20 words), replay, stats, history (`mode=targeted` filter), DailyProgress, daily tasks and the error profile, never the placement board. `GET /api/passages` takes `passageModes` (`practice`, `placement`): `?mode=targeted` answers 400.

### 7c-chain. Nối từ leaderboard (`/api/word-chain`)
Signed-in accounts only. The game runs in the browser, and a finished game is sent as its chain.

**`POST /scores { chain: [{ by: 'bot' | 'me', word }] }`** (1 to 600 links) answers 201 `{ score }`. The server works the score out again (`scoreChain`, `utils/word-chain-rules.ts`):
- Every word has two syllables, is used once, and is in `data/noi-tu-words.ts`. That file is generated by `minigame-words/build-noi-tu.mjs`, from the same list as `FE/public/noi-tu/words.txt`.
- Tones compare wherever the mark sits.
- The chain starts with the bot.
- A player word must chain on the bot word before it: +1.
- A bot word after the player's that does not chain on means the bot was stuck: +2.

A chain that breaks a rule answers 400. A game of 0 points is not saved (`WordChainScore`: user, score, links).

Names and avatars only, never an email. The ranking is worked out at each request (no cache yet).

### 7d. Placement test (`/api/placement`)

The list of passages to pick from is `GET /api/passages?mode=placement` (7e).
**The ranking is kept in memory** (`placement-board-cache.ts`, `cachedBoardRows`): one list for each board (passage, range and, for a week, the week), of every active learner with their best session (`_id`, `wpm`, `accuracy`, `durationMs`; no name), built by one aggregation (`allowDiskUse`) that reads the sessions in the order of the index `{ passageId, isOnPlacementBoard, wpm, accuracy, durationMs, completedAt }` of `TypingSession`, so there is no sort in memory first. It is served for an hour (`PLACEMENT_BOARD_REFRESH_MS`); after the hour it is built again only if something changed (`placementBoardChanged(passageId?)`: a session on the board completed, an admin saved a new minimum accuracy and it moved sessions, or an admin locked, unlocked or deleted learners); if nothing changed, the same list is served for another hour. A new session on the board is therefore shown after the hour at the latest. Requests at the same time wait for one build. Only `active` accounts have a line, so an account saved before the `status` field existed (none) has none until `npm run migrate:user-status` gives it `active`. The names and avatars of the (at most) 50 lines shown are read at every request, so they are always current, and a learner locked or deleted since the build has no line at once (the count `players` and the places only follow at the next build). The week board has its own key per week: a new week starts a new board at once. One process only: with several each would have its own cache. The old index `{ passageId, isOnPlacementBoard, completedAt }` stays in a database that had it until `TypingSessionModel.syncIndexes()` drops it.
`GET /settings` → `{ minAccuracy }`, the accuracy a session needs to be on the leaderboard (the app setting `placementMinAccuracy`, 90 until changed), for the notes of the typing pages. Admins change it with `GET` / `PUT /api/admin/placement/settings` (`admin.route.ts`; `placementSettingsSchema`: `{ minAccuracy }`, a whole number 50 to 100, always sent; `getPlacementSettings` / `updatePlacementSettings` in `placement-board.service.ts`, which save it through `updateAppSettings`); a `PUT` keeps the other app settings (the daily task count). It also sets `isOnPlacementBoard` again with `rebuildPlacementBoardFlags` (`typing-session.service.ts`): one `updateMany` with an update pipeline over every completed placement session, which gives each the flag the rule (`placementBoardRuleExpression`, the same as `isSessionOnPlacementBoard`) and the saved minimum give. It is computed from the rule and the minimum, not from the difference between two minimums, so it fixes a wrong flag too, saving the same value is harmless and running it again changes nothing; it reads every completed placement session once, which is fine because the minimum changes rarely. The order keeps a session being completed right: the minimum is saved first, and `completeSession` reads it again after saving its own flag. Two admins saving at the same time can leave a wrong flag until the next save (accepted). When some flag changed it marks every board as changed (`placementBoardChanged()`): they follow at their next build after the hour.

### 7g. Daily progress, streak and daily mission (SCRUM-31)
A learner's days live in `DailyProgress` (`daily-progress.model.ts`): `{ owner, date: 'YYYY-MM-DD', sessions, missionCompletedAt? }`, one row per learner and day (unique index `{ owner, date }`, which also serves "one learner's days in date order"). ### 7i. Learner daily tasks (SCRUM-112)
Each of a learner's days gets `dailyTaskCount` of the active templates of 7h, the ones that focus on their weakest error types first, measured on the counted sessions of that day like the daily mission; the profile page lists them with their progress. Files: `user-daily-tasks.{model,service}.ts`; the endpoint is in `profile.route.ts` and the recording in `completeSession` (`typing-session.service.ts`). The service never imports typing-session.service.ts, which imports it.
- **`UserDailyTasks`** (`user-daily-tasks.model.ts`): one document per learner and day, unique index `{ owner, date }` (and `{ 'tasks.taskId': 1, date: 1 }` for the chart of the admin list), `date` = 'YYYY-MM-DD' in the learner's zone like DailyProgress (7g). `timeZone` = the zone `progress` is cut in: the learner's zone when the day was made, or the one they moved to since (see **A change of zone** below). `tasks` = the snapshot of the templates picked for that day, in the order shown: `[{ taskId, title, description, type, target, errorType? }]` (`taskId` = the template it was copied from, which may be edited or deleted since). `progress` = the numbers of the day's counted sessions every task is measured on: `{ sessions, durationMs, bestWpm, bestAccuracy, bestErrorAccuracy }`, the last one the best accuracy on each error type of one session with at least `MIN_FOCUS_CHANCES` (5) chances of it (no key for a type without such a session).
- **Generation**: the first time a day's tasks are needed (the first `GET /api/profile/daily-tasks` of the day, the day's first counted session, or its first finished minigame or duel), the service reads `dailyTaskCount` (`getAppSettings`), the active templates in the order they were made, and the learner's weak error types: their last `WEAKNESS_SESSIONS` (20) completed counted Vietnamese sessions (SCRUM-219: `sessionsIn('vi')`, the error types of the tasks are Vietnamese; an English session has no chance of them, so it never moves a focused task) (newest `completedAt` first), `errorCounts` and `opportunityCounts` added up per type, each type only from the sessions with at least `MIN_FOCUS_CHANCES` (5) chances of it, the ones that can move a task focused on it (a type met only a few times in each of 20 sessions would otherwise rank weak and be handed out as a task such sessions never move), then `rankWeakErrorTypes` (pure) keeps the types with at least `MIN_WEAKNESS_CHANCES` (10) chances and one error, weakest first by errors / chances (a tie goes to more errors, then to the order of `WordError`). `pickDailyTasks(templates, weakTypes, count, random)` (pure; the tests pass their own `random`) takes, for each weak type in order and while fewer than `count` are picked, one template that focuses on it at random (a type no template focuses on is skipped), then fills the places left at random from all the other templates: never one twice, at most `count`, all of them when there are fewer. No active template: nothing is stored and the answer is `tasks: []`, so a template activated later that day still gives tasks that day.
- **Snapshot**: stored once, `findOneAndUpdate({ owner, date }, { $setOnInsert: { tasks, progress, timeZone } }, { upsert: true })`: of two requests at the same time, one makes it and the other gets it (MongoDB retries the upsert that lost the race on the unique index; tests that race build the index first with `UserDailyTasksModel.init()`). Its `tasks` are never changed: editing, deactivating or deleting a template, or a new `dailyTaskCount`, applies from the learner's next day. The `progress` stored with it is worked out from the counted sessions already completed that day, in the zone of the request that made it (`timeZone`), so the sessions typed before the tasks were made count.
- **Progress and idempotency**: only the counted sessions (`isCounted`, 7c) of the learner's day count. `completeSession` calls `recordDailyTaskProgress(owner, completedAt)` after `recordCountedSession`, only in the request that completed the session: the day of `completedAt` in the learner's zone (its tasks made if needed) gets its numbers worked out again from all its counted sessions (`dayNumbersOf`, pure) by `updateDayNumbers`, written with `$max` on each field while the day's `timeZone` is the learner's zone (another zone: see the next point). They only grow during a day, so a repeated, late or out-of-order write never takes the day back, and recording the same session twice gives the same numbers. The sessions of a day are read from whole UTC days, from the one before it to the one after it, which hold the day in any zone less than 24 hours from UTC: the IANA ones (UTC-12 to UTC+14) and the offsets such as `+15:00` or `-23:59` that `Intl`, so `isValidTimeZone` and `PATCH /api/profile/settings`, take too. `localDateKey` then keeps the day's own, exactly like DailyProgress. That read and the one of the last 20 sessions go through the index `{ owner: 1, completedAt: -1 }` of `TypingSession`, so they never read all of a learner's sessions.
- **A change of zone**: each request takes the learner's zone of now (`usableTimeZone`) and compares it with the day's `timeZone` as plain strings (two names of one zone, `Asia/Saigon` and `Asia/Ho_Chi_Minh`, only make it work the same numbers out again). When they differ (the learner moved, or the day was made by a request that read their zone before `TimezoneSync` saved the browser's one), the numbers cut in the old zone can count sessions of another day (one session would then count for two days) and miss some of this one, and `$max` would never let them go. The day's next counted session (`recordDailyTaskProgress`) or `GET` then works them out again in the new zone and replaces them with one `$set: { progress, timeZone }`; the `GET` answers the new numbers at once, so the page refreshed after the zone is saved shows the new zone's day. Only once: that `$set` filters on `timeZone: { $ne: zone }`, and a request that finds the day already cut in its zone by another one writes its numbers with `$max` (filtered on `timeZone` too, so numbers of one zone never go into a day cut in another): a late request that read fewer sessions never takes the day back. The `tasks` of the date stay as they were picked.
- **Minigame tasks (SCRUM-300)**: the type `minigames` counts the minigames and ranked duels a learner finished that day (`DayNumbers.minigames`, `dayNumbersOf(sessions, minigames)`; a day stored without it reads as 0). `minigame-times.service.ts` (models only) gives `minigameFinishTimes(owners, from, to)`: the `finishedAt` of finished `MinigamePlay` rows (`chain`, `rain`, `bot`; opened by `POST /api/minigames/plays` and closed by `POST /api/minigames/plays/:id/finish` in `minigame-play.service.ts`, which counts only after `MIN_PLAY_MS[game]` in `config/minigames.ts` (8 s); an open play nobody finished is deleted after a day by a partial TTL index) and the `endedAt` of finished `Match` rows for each player they count for (`countsAsPlayed`: not flagged, win, loss or draw, `unratedReason` not in `UNPLAYED_DUEL_REASONS`). `announceResult` in `match.service.ts` calls `recordMatchMinigames` once a duel is saved, `finishPlay` calls `recordDailyTaskProgress`; both only log a failure. `tasksOfDay` and `updateDayNumbers` read the day's minigames with the sessions (the same UTC window, cut by `localDateKey` in the day's zone), and `hourlyCompletionsOf` gives `completedAtOf` the day's minigame times.
- **Coins for completed tasks (SCRUM-301)**: a template has `coins` (a whole number from 0 to `DAILY_TASK_COINS_MAX` = 100, default 0; 0 = no reward; the admin validator and the model check it). `tasksOfDay` copies it into the learner's `UserDailyTask.coins` with the rest of the snapshot, so changing it applies from the next day, and a day stored before it reads 0 (it pays nothing: finished days are never paid back). `payCompletedTasks` (`user-daily-tasks.service.ts`) runs at the end of `updateDayNumbers`, so every counted session, minigame and duel that moves the day's numbers pays: for each task with coins that is completed on the numbers and whose `taskId` is not in the day's `rewardedTaskIds`, one conditional update (`$ne`) adds it there, and only the request whose update changed the document adds `$inc: { coins }` to the user, so a task is paid once however often a session is recorded and when requests race. Only the server pays: the client never sends coins; `GET /api/profile/daily-tasks` shows only `coins` and `rewarded` for each task and pays nothing. A failed payment is only logged (it never fails the session, minigame or duel) and the next recording of the day pays the task. `User.coins` is the one balance of the avatar shop and the streak reward, never above what it already allows.
- **A task's progress** (`taskProgressOf`, pure), in the unit of its target: `sessions` = the counted sessions; `minutes` = their time in minutes, one decimal rounded down (`Math.floor(ms / 6000) / 10`, so it never shows the target early), completed once the total reaches `target * 60000` ms; `wpm` = the best WPM of one session; `accuracy` = the best accuracy of one session or, with an `errorType` T, the best `round1(100 * (1 - errorCounts[T] / opportunityCounts[T]))` of one session with at least 5 chances of T, 0 until there is one (never below 0: a word without a vowel mark can be typed with one, so MARK_WRONG can have more errors than chances). Completed when the progress reaches the target.
- `GET /api/profile/daily-tasks` (`authGuard`) → `{ date, tasks: [{ id, title, description, type, target, errorType?, progress, completed }] }`: `date` = today in the learner's zone (`DEFAULT_TIMEZONE` when missing or unknown, `usableTimeZone` of daily-progress.service.ts), the progress from numbers cut in that zone (worked out again first after a change of zone), the tasks in the order of the snapshot, `id` = the template's id, `description` '' when there is none, `errorType` only on a focused accuracy task; never the owner or the stored `progress`. 401 without a token; the token of a deleted account answers 404 `User not found`, like `GET /api/profile/streak`.
- **Failures**: a failed write of the daily tasks is logged (`Daily tasks not updated, ...`) and the completion still answers 200, like DailyProgress: the session is saved, a retry would get 409. No rebuild script is needed: the next counted session of the day works the numbers out again from all the day's sessions, and tasks made later start from the sessions already counted. Only today's tasks are shown, so a past day whose last write failed stays behind unseen.
- **Completions for the admin list** (`hourlyCompletionsOf(taskIds, now)`, the `completions` of `GET /api/admin/daily-tasks`, 7h): a learner's day completes a task at the counted session that first brings it to its target (`completedAtOf`, pure: the day's sessions oldest first, added up one by one with `dayNumbersOf` and measured with `taskProgressOf`), so no completion time is stored and the days made before the chart count too. It reads the days that had some of the templates from the UTC day before the first of the 24 hours on (a day that ends inside them starts at most a day before them, in any zone; index `{ 'tasks.taskId': 1, date: 1 }`), keeps the tasks their stored numbers have completed, reads the counted sessions of their owners once (oldest first, through `{ owner: 1, completedAt: -1 }`), cuts each day in its own `timeZone` like its numbers, and puts the learner in the hour of the completing session when it falls in the 24 hours: a task completed before them is left out, even when sessions of the same day fall inside them. A learner counts once an hour and once in all, also when two of their days had the task (yesterday evening and this morning).
- Deleting a user deletes their `UserDailyTasks` (`deleteUsers` in `admin-user.service.ts`).

### 7i-b. Error profile (SCRUM-27)
For each error type of one typing language (7m; SCRUM-219: the set of the language, from the sessions of that language only), the error rate of the learner's last counted sessions, a level and a trend against the sessions before them; the profile page shows it in the learner's typing language. File: `services/error-profile.service.ts`, which imports only models, so no service cycle starts there; the endpoint is in `profile.route.ts`.
- **Worked out when read, never stored**: `getErrorProfile(userId, language?)` (the learner's `settings.typingLanguage` when no language is given) reads the learner's last `2 × PROFILE_WINDOW` (20) completed counted sessions of that language (`sessionsIn`) that have `opportunityCounts` (sessions saved before the chances were counted have none and take no place), newest `completedAt` first, through the index `{ owner: 1, completedAt: -1 }`, only `errorCounts` and `opportunityCounts`, and hands them to `computeErrorProfile` (pure). So a session is in the profile as soon as `completeSession` has saved it (nothing is written there), a new rule applies to every learner at once, and there is nothing to rebuild or to delete with the user. The token of a deleted account answers 404 `User not found`, like the other profile endpoints.
- **Windows**: the current window is the first `PROFILE_WINDOW` (10) of those sessions, the previous one the next 10. Per type: `errors` and `opportunities` = the totals of the current window (a missing count is 0); `rate` = errors / opportunities in %, one decimal, like the session stats (7c), 0 without a chance and at most 100 (a vowel mark typed on a word without one is a MARK_WRONG error on a word that gave no chance of it); `previousRate` = the same in the previous window.
- **Level** (`levelOf`): `insufficient_data` under `MIN_PROFILE_OPPORTUNITIES` (20) chances in the current window; else `weak` when `errors × 100 ≥ WEAK_RATE × opportunities` (`WEAK_RATE` = 15 %), compared in whole numbers because a sum of decimals misses the edge (`0.15 >= 0.05 + 0.1` is false in JavaScript); else `ok`.
- **Trend** (`trendOf`): `insufficient_data` while either window has fewer than 20 chances; else a two-proportion z-test between the windows (pooled rate p, `z = (p₁ − p₀) / √(p(1 − p)(1/n₁ + 1/n₀))`): `improved` when z ≤ −`TREND_Z` (1.96), `worse` when z ≥ 1.96, otherwise `unchanged`, also when the standard error is 0 or not a number (no error at all, or more errors than chances). The test weighs a change by the chances there are: 30 % → 20 % on 30 words with đ is noise, 6 % → 3 % on 400 words is a trend. No record is kept (no lowest rate ever): the trend is always these 10 sessions against the 10 before.
- `GET /api/profile/error-profile?language=vi|en` (`authGuard`, `languageQuerySchema`) → `{ language, window, minOpportunities, weakRate, sessionsUsed, types: [{ type, errors, opportunities, rate, level, previousRate, trend }], weakTypes, rankedTypes }`, always the signed-in learner's own: the thresholds come along so the frontend never writes them; `sessionsUsed` = the sessions of the current window (0 to 10); `types` one per type of the language in the order of its set (`WordError` or `EnglishError`); `weakTypes` = the `weak` ones by rate, then errors, then the order of the set; `rankedTypes` = every type with a level (`weak` or `ok`) in the same order, so `weakTypes` is its start. 401 without a token.
- `getWeakErrorTypes(userId, limit = 2)`: the learner's weak Vietnamese types (from their Vietnamese sessions, whatever their typing language), highest rate first, at most `limit`. `getTopErrorTypes(userId, limit = 2)`: the first `limit` of the Vietnamese `rankedTypes`, weak or not, from the Vietnamese sessions too: the focus of a Weak spots lesson without an error type chosen (US3.2, 7c-targeted). The daily tasks (7i, `rankWeakErrorTypes`) and word rain (`focusFor` in `rain.service.ts`) still pick weak types their own way.
- Every mode counts (practice, placement, Weak spots lessons, daily), but only counted sessions (`isCounted`, 7c): abandoned, unfinished, too short, too fast or too long sessions never change it.
- The demo learner of `npm run seed` has a profile with hỏi/ngã weak and improving and the other types ok (`demoErrorCounts` in `scripts/seed.ts`: the chances in the shares of the starter passages); demo sessions seeded before it get its counts on the next run (`fillDemoErrorCounts`).

### 7i-c. Vowel × tone grid (SCRUM-29, US4.1)
For each of the 12 Vietnamese vowels (a ă â e ê i o ô ơ u ư y) and each of the 6 tones (ngang, sắc, huyền, hỏi, ngã, nặng), how often that vowel was in a target word of that tone (`seen`) and how often the learner typed the word wrong at that vowel or tone (`wrong`), in their last counted Vietnamese sessions; the Progress page draws it (the Vowel × tone page)
- **Worked out when read, never stored**, like the error profile: `getVowelToneGrid(userId)` (`services/vowel-tone.service.ts`) reads the learner's last `PROFILE_WINDOW` (10) completed counted sessions of `language: 'vi'` (`sessionsIn('vi')`: the vowels and tones are Vietnamese, whatever they type in Practice), newest first, and only their `words` (`target`, `typed`); the pure `computeVowelToneGrid(sessions)` does the counting.
- **Seen**: each vowel of a target word is one sighting of (vowel, the tone of the word): "hoa" is (o, ngang) and (a, ngang), "bà" is (a, huyền); ơ and ư are vowels of their own. **Wrong**: the typed word has another tone (`classifyWord` says `TONE_WRONG` or `HOI_NGA_CONFUSION`: every vowel of the word is wrong), or the typed word has as many letters as the target (each letter has its place) and that vowel was typed as another letter or with another mark. A wrong consonant, or a word typed with another length, is not blamed on a vowel (and a tone error is).
- **Examples**: up to `MAX_EXAMPLES` (3) different `{ target, typed }` words typed wrong at a cell, the newest first.
- `GET /api/profile/vowel-tone` (`authGuard`; the learner reads only their own) → `{ language: 'vi', window, minSeen, sessionsUsed, vowels, tones, cells: [{ vowel, tone, seen, wrong, examples }] }`: always all 72 cells (vowel by vowel), `minSeen` = `MIN_VOWEL_TONE_SEEN` (5): the frontend greys a cell seen fewer times and never writes the number. No email and no other field of the sessions is sent.

### 7i-d. Error rate over time (SCRUM-30, US4.2)
The error rate of each error type of one typing language in each period of the Progress page's chart (the Error rate chart next to the WPM chart)
- **Worked out when read, never stored**: `getErrorTrend(userId, range, date, language)` (`services/error-trend.service.ts`) sums, per local day of the learner's time zone, the `errorCounts` and the `opportunityCounts` of every type of the language over their completed counted sessions (`sessionsIn`); the pure `buildErrorTrend` joins the days into the periods.
- **Periods**: the same as the WPM chart (`chartKeys`, `keyOfDay`, `firstDayOf` of `monthly-progress.service.ts`): `year` = 12 months, `month` = blocks of 7 days, `week` = days, with `date` = the period that holds that day; a period that has not started is left out.
- **Rate**: the sum of the errors over the sum of the chances of the period's days (not an average of the days), in %, one decimal, at most 100. A period with no chance of a type has `null`: a gap in the line, never 0.
- `GET /api/profile/error-trend?range=year|month|week&date=YYYY-MM-DD&language=vi|en` (`authGuard`, `monthlyProgressQuerySchema`; the learner's own sessions only; the learner's Practice language when `language` is missing) → `{ range, language, types, points: [{ key, rates: { <type>: number | null } }] }`: the five Vietnamese types or the six English ones, in the order of their set. A deleted account's token answers 404.

### 7j. Ranked duels (`/api/matches`, ranked duel design phase 3)
Signed-in accounts only. Files: `match.model.ts`, `match.{validator,controller,route}.ts`, `services/match.service.ts` (rules), `services/match-view.ts` (room codes, `pickRankedPassage`, `toPublicMatch`) and `services/match-hub.ts` (live part). The `Match` document is the truth; the hub keeps the open SSE streams and the timers (countdown, time limit, disconnect grace, closing the streams of a finished room) per room code, in memory, so the backend must run as one process (see the `ponytail` note there). Every change of a room goes through `withMatchLock(code, ...)`, so two players finishing at the same moment cannot both win. Durations are in `matchSettings` (tests shorten them, `resetMatchHub()` puts them back).
- Room: `POST /` creates a `waiting` room (6-character code without `0 O 1 I`, unique among open rooms by a partial unique index; a random published public English passage of 30–80 words, 404 without one); `POST /:code/join` (any case; 400 own room, 409 full or already in another open room); `GET /:code` and `GET /:code/events` only for its players (others 404); `POST /:code/leave` (guest leaves, or host cancels; during a match the leaver forfeits). A waiting room older than 10 minutes is cancelled when it is next read. Players are shown by display name or `Anonymous player`, never the email; the passage words only once the countdown starts; typed words never leave the server.
- Race: `POST /:code/ready { ready }`; both ready → `countdown` (3 s, `countdown` event) → `running` (`startedAt` by the server clock, time limit `MAX_SESSION_MS`). `POST /:code/progress { typedWords, typedAtMs, done }` sends everything typed so far; the server grades it with `gradeWords`, streams `progress` (counts only) and applies the rules: a finisher with ≥ 90% correct wins at once; under 90% waits for the other; both under 90% or time up → more correct words wins, equal is a draw; the match `wpm` uses the same `computeWpm`; over `MAX_COUNTED_WPM` loses and flags the match. 400 when progress goes back by more than one word, times go down or past the limit, or `done` comes early; 409 when the match is not running or the player already finished. `POST /:code/rematch` after the end opens a new room and sends a `rematch` event with its code on the old stream.
- Streams: `text/event-stream` with `state`, `countdown`, `progress`, `result`, `rematch`, `presence`, `resume` events and a ping every 15 s; the client reads it with `fetch` and the `Authorization` header (never a token in the URL). Leaving, connection and time (SCRUM-154): a player who leaves (`POST /:code/leave`) or whose stream stays closed `disconnectGraceMs` (15 s) during a match does not finish (DNF, stored as `forfeit`) and the other one wins; reopening it in time cancels that. A drop is told to the room as `presence` `{ userId, connected: false, forfeitAt }` and the comeback as `{ userId, connected: true }`; a player who opens the stream while the other one is away gets that `presence` at once. A race player who reopens the stream gets `resume` `{ typedWords, typedAtMs }` (only to them) to go on from the saved words. When both players are away the first timer ends the match with both `forfeit`, unrated (`abandoned`). The race still ends when both finish or at `durationMs`. Progress has its own limit (20 a second per player) and skips the global one.

**Rain duels** (rain duel design, `kind: 'rain'`): `POST /api/matches { kind }` (no body or `race`: the race as before) opens a room with the words of every published English passage (`pickRainWords`, `rainWordsFrom`: lower case, letters only, 3 to 10 letters, shuffled; 404 under 20 words) and no passage. Lobby, ready, countdown, forfeit, rematch (same kind) and the stream are shared with the race; `POST /:code/progress` refuses a rain duel and `POST /:code/rain { text }` (same per-player limit, skips the global one) refuses a race. The rules are in `services/rain-duel-rules.ts` (`rainDuelSettings`: 3 lives, 6 lanes, 120 s, thrown words ×1.15 faster, 150 ms grace, and `paces` per tier: spawn gap, fall time, thrown cap and longest word, from Bronze 2800 → 1600 ms / 9000 → 6000 ms / 1 / 6 letters to Diamond and Legend 1800 → 800 ms / 6500 → 3500 ms / 3 / 10; `buildRainSchedule(words, rand, pace)` one schedule for both players, `wordsForPace`, `pickThrownWord`, `isInTime`, `rainOutcome`). The pace is the tier of the two players' average rain rating when the countdown ends (`match.rainTier`, in the public match). `services/rain-duel.service.ts` runs a duel in memory: `startRainDuel` (inside the lock, before the match is saved as running) spawns the schedule on both sides and gives each word a landing timer at `bornAt + fallMs + graceMs` (every timer takes the match lock); `hitRainWord` hits the matching word of the player's side that lands first, if the server got it in time, and throws another word of the rain, one not falling on the other side yet, there (a thrown word is never thrown back; over the cap it waits, and gets its word when it falls); a landing takes a life; K.O. or the time ends the match through `endRainDuel` in `match.service.ts` (lives, hits and thrown saved on the players, `rateMatch` on the rain rating). Events: `rain` with `type` `spawn` / `hit` / `land` and `serverNow`, and `snapshot` (both sides) sent to a player whose stream opens during the duel. `finish` stops the rain whatever ended the match. A running rain match that this process never started (`wasStartedHere`: only a restart forgets) ends unrated as `interrupted` when it is next read.
### 7k. Elo and seasons (`/api/ranked`, `/api/admin/seasons`, ranked duel design phase 5)
Files: `season.model.ts`, `season-rating.model.ts`, `services/season.service.ts` (seasons, tiers), `services/rating.service.ts` (Elo), `services/ranked.service.ts` (API), `ranked.{validator,controller,route}.ts`.
- Seasons: 8 weeks; exactly one `active` (partial unique index). No background job: `currentSeason()` opens season 1 the first time one is needed and closes a season past `endsAt` on the next request; `closeSeason(id)` (also the admin's early close) opens the next one. The soft reset is lazy as well: `startRatingFor(user, season)` starts a player at `round(1000 + (rating − 1000) / 2)` of their rating in the season before (1000 without one) when their first match of the new season is rated, and `/me` shows that start before it. Each season has a `rewardItem` (the next of `SEASON_ITEMS` in `avatar-catalog.ts`). On close (phase 6) every player who reached Gold gets the items of their peak tier and every tier under it (`TIER_REWARDS`, cumulative) plus the season item; an item already owned pays its price, or `OWNED_REWARD_COINS` (100) for an item not sold. `SeasonRating.rewardedAt` is claimed right before the grant, so a player is rewarded once. The peak is the best rating after a match of the season, never the start (a strong player starting at 1250 has not reached Gold yet). Giving rewards never fails the request that closes the season (it is logged); what a failure left out is given when that season is closed again.
- Coins (phase 6): a rated match gives win 20, draw 10, loss or forfeit 5 (`MATCH_COINS` in `rating.service.ts`), at most `DAILY_COIN_LIMIT` (200) a day in Vietnam time; what was earned is kept on the match player (`coins`, shown on the result), so the daily total is summed from the matches.
- Elo: every place in `match.service.ts` that can finish a match calls `rateMatch(match)` before saving it. It settles the match once in the current season (an atomic claim on `match.season`, so two requests ending the same stale race rate it once): `E = 1 / (1 + 10^((Ro − R) / 400))`, `R' = round(R + K × (S − E))`, K 40 for a player's first 10 matches of the season then 32, S 1 / 0.5 / 0 (forfeit 0). Not rated (`rated: false`, `unratedReason`): `not-started` (left during the countdown), `flagged` (WPM cap), `pair-limit` (the two players already have 3 rated matches since 0:00 Vietnam time, UTC+7). Players get `ratingBefore` / `ratingAfter`.
- `GET /api/ranked/me`: season, rating (1000 before the first rated match), peak, tier, counts. `GET /api/ranked/leaderboard`: `paginate` over the season's ratings with 5 matches or more, best first, with rank, display name (or `Anonymous player`), avatar, tier, win rate; never an email. Tiers (`tierFor`): Bronze < 1100 ≤ Silver < 1250 ≤ Gold < 1400 ≤ Platinum < 1550 ≤ Diamond < 1700 ≤ Legend.
- **Kinds of match** (rain duel design §10): every `SeasonRating` has a `kind` (`race` or `rain`, the match `kind`); `rateMatch` moves the rating of the match's kind only, `startRatingFor(user, season, kind)` soft-resets each kind from its own rating, `GET /me?kind=` and `/leaderboard?kind=` (default `race`, 400 for another value) read one kind. The season rewards loop over every rating, so each kind gives the rewards of its tier (an item already owned through the other kind is paid in coins). Ratings from before kinds: `npm run migrate:rating-kinds` (sets `race`, drops the old `season_1_user_1` index).
- Admin: `GET /api/admin/seasons` (newest first; each season has `participants: { race, rain }`, the players with at least one match of that kind in it, counted with one aggregate for the page) and `POST /api/admin/seasons/:id/close` (answers the new active season; closing a closed one changes nothing). There is no "open season": closing opens the next.

### 7l. Avatar (`/api/avatar`, ranked duel design)
Signed-in accounts only. Files: `avatar.{validator,service,controller,route}.ts`, `data/avatar-catalog.ts` (prices and rules) and the generated `data/avatar-items.ts` (every item by slot; run `node minigame-sprites/build-layers.mjs`, never edit it by hand). `User` has `avatar` (the look: `skin, face, hair, top, bottom, shoes` and the optional `headwear, accessory, back, effect`, `null` = empty; defaults `DEFAULT_AVATAR`, also for accounts saved before the field), `ownedItems` (`slot:item`, bought or won items only) and `coins`. `unlockOf(slot, item)` says how an item is unlocked: `free` (starter items), `shop` (a price in coins, by slot), `tier` (a season tier reward, never sold) or `season` (the item of a season, never sold), `undefined` for an item the slot does not have. `POST /buy { item: 'slot:item' }` buys a `shop` item and answers the catalog: one conditional update (`coins >= price` and not owned) spends and adds it, so two buys at once never go below zero or buy twice; 400 `This item is not sold` / `Not enough coins` / `Unknown item`, 409 `You already own this item`. `GET /catalog` → `{ avatar, coins, slots: { [slot]: [{ id, unlock, owned }] } }`; `PUT /` with a whole look → the user, 400 `Unknown item: <slot> <item>` or `Item not owned: <slot> <item>` (nothing saved). Only the account itself sees its `coins` and `ownedItems` (`/me`, the catalog); no learner endpoint returns another user.

### 7m. Word error sets (`utils/vietnamese-errors.ts`, `utils/english-errors.ts`)
Each passage language has its own set of word errors, in a pure TypeScript file with an identical copy in the frontend (`FE/src/shared/lib/`, only the first comment differs): keep each pair identical, tests included. Each file names the errors of a typed word against its target word (`classify…`: an empty list means right, each error once, in the order of the set) and the errors a target word gives a chance of (`tag…`, the "error opportunities": rate of an error = times it happened / times it could have happened).
- **Vietnamese** (`WordError`, `classifyWord`, `tagWord`, SCRUM-24): `BASE_LETTER`, `D_MISSING`, `MARK_WRONG`, `TONE_WRONG`, `HOI_NGA_CONFUSION`. The Vietnamese passages use it: the Vietnamese sessions (7c: Practice in Vietnamese and the placement test), the word bank, word rain, the daily tasks of an error type and the Vietnamese error profile (7i-b).
- **English** (`EnglishError`, `classifyEnglishWord`, `tagEnglishWord`, SCRUM-218, US2.6): English has no tones or vowel marks, so its errors are about the letters, their case and the punctuation attached to a word. Letters are letters and digits (`\p{L}\p{M}\p{N}` after NFC); every other character is punctuation. The two words are lined up with the fewest edits (Damerau–Levenshtein: a character typed as another, left out, one too many, two neighbours the other way round) and each edit is named after the character of the target, a character too many after the typed one:
  - `LETTER_WRONG`: a letter typed as another character (`car` for `cat`, `far,` for `farm`). Chance: words with a letter.
  - `LETTER_MISSING`: a letter left out (`th` for `the`). Chance: words with a letter.
  - `LETTER_EXTRA`: a letter too many (`thee`). Chance: every word.
  - `LETTERS_SWAPPED`: two different letters side by side typed the other way round (`teh`, `from` for `form`). Chance: words with two different letters side by side.
  - `CASE_WRONG`: the right letter in the wrong case (`the` for `The`, Caps Lock). Chance: words with a letter that has a case: Caps Lock and Shift reach every letter, as a tone reaches every Vietnamese word.
  - `PUNCTUATION_WRONG`: a punctuation mark of the word typed wrong, left out or out of place (`bread` for `bread,`, `dont`, `do'nt`), or a stray one (`bread,` for `bread`). Chance: words with punctuation, so a stray mark, like a vowel mark typed on a Vietnamese word without one, is an error on a word that gave no chance of it.

  Practice in English grades with it (SCRUM-219: a session of `language: 'en'`, 7c, and the English error profile, 7i-b); ranked duels only count the right words (`gradeWords`), and a word is right only when it is typed exactly, whichever set grades it.
- **Passages**: `computePassageStats` counts `tagCounts` with the set of the passage's `language` (`tagWord` for `vi`, `tagEnglishWord` for `en`). `tagCounts` holds the types of both sets (`TagCounts`), the other language's at 0, and is counted again whenever `content` or `language` changes. `npm run rebuild:tag-counts` (`rebuildTagCounts` in `scripts/rebuild-tag-counts.ts`) counts `wordCount` and `tagCounts` of every passage again: run it once after deploying SCRUM-218 (English passages saved before have all 0) and after changing a `tag…` function. It writes each passage on the condition that its `updatedAt` is still the one it read (a passage saved meanwhile keeps the counts of that save), with `timestamps: false` so `updatedAt`, which orders the review queue (7b), does not move; safe to run many times.

### 8. Errors (`utils/app-error.ts` + `errorMiddleware`)

### 9. Models
`<Name>Document` interface + `Schema`, `{ timestamps: true }`, DB constraints (`required`, `maxlength`, `enum`), indexes for the default list query, and a `toJSON` transform that removes `__v` and any private field. The User model strips `password`, `otpCode`, `otpExpiresAt`, `resetToken`, `resetTokenExpiresAt` in `toJSON`, so returning a user **document** is safe. `.lean()` and `aggregate()` return plain objects that skip `toJSON`: with those, `.select()` / `$project` the public fields explicitly.

### 7n. Plans, subscriptions and passage limits (US11.1)
Files: `subscription.model.ts`, `subscription.service.ts`, `passage-lock.service.ts`, `admin-plan.{service,controller}.ts`, `plan.{controller,route}.ts`, `plan.validator.ts`. A learner's plan is the newest row of `Subscription` in effect (one row for each term, with its own `startsAt` and `expiresAt`; a row can start in the future; rows are only added, and the only edits are `endedAt` and `cancelledAt`): `getCurrentSubscription` answers `{ plan, expiresAt }` (the end of the last term), Free without a row, and Free for a Premium term past its end, writing then the one `auto` Free row that starts at the end (a unique partial index on `{ user, startsAt }` for `source: 'auto'` keeps it to one when reads come together). ## Security Rules

- Private fields are removed by the model's `toJSON`; add new private fields to `PRIVATE_USER_FIELDS` (or the model's own transform).
- Passwords hashed with bcrypt (`utils/hash`). OTP and reset codes are single-use. **Do not change the OTP functions** (`utils/otp.ts`, `createUserWithOtp`, `issueOtpForUser`, `issueResetToken`, OTP/reset handlers).
- Rate limits: 300 req / 15 min globally, 20 req / 15 min on `/api/auth/*` except `/me` (both off in tests). Behind a reverse proxy set `TRUST_PROXY=1` (number of proxies) so limits apply per client, not per proxy.
- `npm run seed` refuses to run with `NODE_ENV=production` (the demo admin has a public password). It also gives `demo@example.com` sessions (`seedDemoSessions`: a counted placement test 8 months ago, practice sessions since, `passageId` `demo-seed` as the mark: a learner who has any is not seeded again; each one is counted for their days with `recordCountedSession`).
- Ownership checks live in services; other users' resources answer 404.
- Uploads: memory storage, 5 MB, JPEG/PNG/WebP/GIF only (`imageUpload`).

## Playbook: Add a New Feature Endpoint

1. `npm run gen:module -- <name>` from the repository root (copies `notes`, registers the router), then change the fields. Or by hand:
2. **Model** — `models/<name>.model.ts` (constraints, indexes, `toJSON`).
3. **Validator** — create / update / list-query schemas in `validators/<name>.validator.ts`.
4. **Service** — queries with `accessFilter`, `paginate`, `throw notFound(...)`.
5. **Controller** — thin handlers; 201 on create, 204 on delete.
6. **Route** — `authGuard`, `requireRole`, `validate` per endpoint; mount in `app.ts`.
7. **Env** — new variables in `config/env.ts` and `.env.example`.
8. **Tests** — integration test like `notes.test.ts`.
9. **Verify** — `npm test` and `npm run build`.

## Do / Don't

- ✅ Keep controllers thin; put queries and access rules in services.
- ✅ Validate body, query and params with `validate`.
- ✅ Throw `AppError` helpers for expected failures.
- ✅ Use `paginate` for every list.
- ❌ Don't send error responses by hand or wrap handlers in try/catch.
- ❌ Don't read `process.env` outside `config/env.ts`.
- ❌ Don't return documents with private fields that `toJSON` does not strip.
- ❌ Don't add new top-level folders without a clear layer justification.
